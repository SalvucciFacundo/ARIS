# Proposal: ARIS Gateway Multiplexer (Telegram & Discord)

## Intent / Problem Statement
ARIS is currently limited to CLI and TUI on local terminals. Users need remote access via Telegram and Discord to trigger autonomous visual generation, route to subagents (`@director`, `@anime`, etc.), and receive rendered images in real-time. Without a remote gateway, the platform cannot be used in collaborative or mobile environments.

## Proposed Solution
Build a concurrent Gateway Multiplexer with modular Telegram and Discord adapters located under `internal/adapters/gateway/`. These adapters will integrate securely with `AgentService` and `SubagentManager`. The multiplexer (`aris gateway`) will manage the graceful lifecycle of all enabled adapters, parsing commands and `@subagent` syntax to trigger backend processing and deliver images back to the user.

## Scope & Key Features
- **Configuration**: Extend `~/.aris/config.yaml` to include bot tokens, enabled flags, and allowlists (chat IDs, channel IDs).
- **Telegram Adapter**: Polling mechanism, handling commands (`/gen`, `/subagents`, `/backends`, `/memory`), `@subagent` prompt routing, and uncompressed document/photo delivery.
- **Discord Adapter**: Message/slash command listener, channel/user allowlist validation, and image attachment uploads.
- **Gateway Multiplexer**: A unified entry point (`aris gateway`) to initialize, start, and gracefully shut down all enabled messaging adapters.
- **Strict Security & Access Control**: Reject unauthorized users and channels strictly before any LLM or image generation backends are invoked.

## Affected Areas
- **Config**: `internal/config/config.go` (new gateway secrets, flags, and allowlists).
- **Adapters**: New package `internal/adapters/gateway/` containing `telegram.go`, `discord.go`, and `multiplexer.go`.
- **CLI**: New Cobra command `cmd/gateway.go` to launch the multiplexer.
- **Core Interfaces**: Minimal updates or specific dependency injection to pass `AgentService` to the gateway package.

## Alternatives Considered
- **Raw HTTP webhooks vs Long-polling/WebSocket**: Long-polling (Telegram) and WebSockets (Discord) are chosen over raw HTTP webhooks to avoid requiring users to configure reverse proxies/ngrok for local instances.
- **Embedded mini-server vs dedicated bot libraries**: Decided to use standard, robust libraries (`go-telegram-bot-api` and `discordgo`) rather than implementing raw protocol logic to ensure maintainability and handle file upload abstractions cleanly.

## Risks & Mitigations
- **Concurrency Spikes**: Multiple simultaneous generation requests could overwhelm local backends.
  *Mitigation*: Implement worker pools or rate-limiting within the multiplexer/adapter layer.
- **Token Security**: Exposing bot tokens in logs or errors.
  *Mitigation*: Mask tokens in logs and load strictly from secure YAML config.
- **Large Image Uploads**: Exceeding platform attachment size limits.
  *Mitigation*: Check file size before upload; optionally compress or warn the user if the image is too large.
- **Access Control Failures**: Unauthorized users burning GPU resources.
  *Mitigation*: Fail-closed allowlists evaluated at the earliest possible adapter ingress point.

## Out of Scope (Non-goals)
- Web UI or browser frontend (reserved for a separate Wails v2 milestone).
- Interactive button-based image editing or callback queries for complex multi-step workflows (future milestone).

## Rollback & Success Criteria
- **Rollback**: Disable the gateway flags in `config.yaml` or revert the CLI command addition; core CLI/TUI will remain unaffected as the gateway is strictly additive.
- **Success Criteria**: A user in an allowed Telegram chat or Discord channel can issue `/gen @anime A cyberpunk city`, the image is generated by the local ARIS engine, and the resulting file is successfully uploaded back to the chat.

## Proposal Question Round
*Assumptions needing user review before Spec:*
1. **Concurrency Handling**: Should the gateway actively queue requests (e.g., max 1 concurrent generation) to protect local GPU VRAM, or just pass them to the `AgentService` and let it fail/queue?
2. **Allowlist Granularity**: Do we need both User-level and Chat/Channel-level allowlists for Telegram/Discord, or is Channel-level sufficient for v1?
3. **Response UX**: While generating (which might take seconds/minutes), should the bot send an initial "Generating..." placeholder message and edit it when done, or only send the final image?
